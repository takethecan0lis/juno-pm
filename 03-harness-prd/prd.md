## Problem & user

RocketShip PMs need this handled: Describe Juno's role and task: You are Juno PM, an AI Associate PM and business analyst for Drew's agent workplace. You recommend and run bounded spikes; you never edit a backlog, send, post, spend or delete. Purpose: work across Drew's projects sits waiting because nobody checks which items already meet the Definition of Ready and which need a spike first. Each run, read every permitted project's backlog and journal. Find items that meet the Definition of Ready and can run without Drew's input, run spikes on items where a spike would make them ready, estimate WSJF where it is missing, and deliver one digest ranked by WSJF. Success: Drew accepts most digest items as truly ready, in one decision each. Archetype: split. The digest is a tool-using copilot. The spike runner is a supervised agent with a narrow auto-approve set, and it needs the Module 5 evals before it ships.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Sources: each permitted project's _Project/Backlog.md, _Project/Where-We-Left-Off.md and _Project/Decision-Log.md; WSJF scores where a backlog row has them; the Definition of Ready text (location still to confirm, marked "draft, not adopted" until it is a file). Methods: the skill file, the Definition of Ready and the WSJF formula ride in the prompt (small, stable, always relevant); project files are fetched on demand with a read tool. No retrieval index and no load-everything, because there are many projects and each file is small and current. Left out on purpose: restricted projects, personal files, anything marked confidential, and any project folder not named in the permitted list. Freshness: files are read live on every run and never cached; a file older than 2 days is labelled stale in the digest. When a source is unreachable: the digest lists the project as "not read" with the reason and never shows it as clean.

**How fresh must it be**

A change in a source shows up in the next run, because files are read live and never cached. A file not edited in more than 2 days is labelled stale in the digest, so I know its status may be out of date. If a source cannot be read, the digest lists that project as "not read" with the reason and never shows it as clean. The run continues with the other projects.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

Turn ceiling: one pass per run, at most 6 tool calls per project and 40 per run. Each spike has its own ceiling of 15 turns, and a run starts at most 3 spikes. Escalation trigger: stop and hand back to Drew after 3 consecutive failed reads or tool calls, or when a spike has only questions left that Drew can answer. A spike ends when every reachable area is done; open questions are written down, not guessed. A run ends when the digest is drafted and every project is either read or listed as not read. Latency and cost target (placeholders until Module 4): a full run in under 10 minutes and under $2.00 per run, with the actual cost shown in the digest footer. Turns multiply cost, so spikes are the part to watch.

**Latency and cost target**

A full run finishes in under 10 minutes, and reading any single project takes under 60 seconds. Cost stays under $2.00 per run: the digest under $0.50, and each spike capped at $0.50, with at most 3 spikes. The actual cost of every run is printed in the digest footer. If a run passes either limit, it stops and reports what it finished.

## 04 Memory · Data Requirements

**What persists, at what scope**

Persists: the last 4 digests, so Juno can say what changed since the previous run and does not repeat items; and a spike log (question, status, findings, open questions) so a spike does not run twice. Scope: team of one, nothing crosses between projects except the digest, and restricted projects never appear in it. Expiry: a digest is stale after 7 days; spike findings are stale after 14 days; open questions stay until Drew answers them. Write rules: Juno writes digests and the spike log, only to its own scratch and digest folders. Drew's corrections (for example "this was not ready") outrank any stored output and are kept for 90 days. A stale entry is labelled stale, never used as if current.

**Expiry and write rules**

Digests expire after 7 days and spike findings after 14 days. Open questions stay until I answer them. Expired entries are labelled stale and never used as if current. Juno writes only to its own digest and scratch folders, and nowhere else. If one of my corrections (for example "this item was not ready") disagrees with something Juno stored, my correction wins, and it is kept for 90 days.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | blocked |
| send | blocked |

**Justification**

read: auto. The blast radius is nothing; a wrong read only wastes tokens. draft: auto (estimate WSJF, draft the digest, recommend a spike). A wrong call means Drew reads a bad suggestion and nothing changes. start a spike: auto, but only a spike as defined in Tools, which writes to a scratch folder and is fully recoverable. This was changed from confirm on 2026-11-21 so work runs without Drew. Anything beyond that definition, such as a larger cost, a new tool or a new data source, is confirm. write: editing a backlog is blocked in V1, because the team relies on that state. send: blocked. Anything that leaves Drew's own files, such as email, a post or a message, cannot be taken back. Spend, accounts and credentials are blocked.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

The check before Drew sees the digest: every item cites its source file and item ID, and every "ready" call names each Definition of Ready criterion it meets, with a citation. A second pass by a separate checker (not the agent that wrote the digest) compares each cited claim to the real file. The bar: no uncited item is shown as ready. Every spike finding is labelled evidence or guess and cites a source, and a spike can only recommend that an item is ready; Drew accepts it. Failure behaviour: an item or finding that fails the check is returned labelled "unverified" or "NEEDS CLARIFICATION" and is never silently dropped. A project that could not be read is listed as not read. Until Module 5, Drew spot-checks by hand.

**Failure behaviour**

If an item or finding fails the check, Juno still shows it but labels it "unverified" or "NEEDS CLARIFICATION" and says why, for example "no source found" or "criterion not met." It is never silently dropped and never shown as ready. A project that could not be read is listed as "not read," with the reason. If more than half the items in a digest fail the check, the digest is marked "low confidence" at the top and I review it before using it.
